Declarative interactions for customized built-in web components, and the host that runs them.

You write plain HTML. is="interactable-<tag>" turns an element into a host; an on-* attribute makes it a trigger; implements="…" makes it a receiver. No page JavaScript.

Quick start

<script type="module">
  import "interactably/dist/cdn/revealable.js";
  import { defineInteractableHost } from "interactably/dist/cdn/interactably-core.js";
  defineInteractableHost("button");   // idempotent
</script>

<button is="interactable-button" on-click="#modal.show()">Open</button>
<dialog is="interactable-dialog" id="modal" implements="revealable">…</dialog>

Clicking the button sends the verb show() to #modal, which implements revealable.

Try it — a price calculator

The total is a formula, sum('#list .amount'), re-evaluated by #total.compute() after every change. No JavaScript was written for this card.

Why

  • 1
    Why should an interaction live in a .js file when the trigger is right here in the markup? The phrase that fires on click belongs on the button. One attribute, one phrase language: on-click="#pop.show().focus()".
  • 2
    Why should a receiver be a reference a script holds, when the DOM already has addresses? Ids are the addresses; implements is the capability. #id.verb() is member access — the element has show because it implements revealable.
  • 3
    Why should debounce, throttle and once mean a dependency on an event library? They are phrase modifiers: #echo.set(this.value).debounce(300), #tour.show().once(). No imports.
  • 4
    Why should "when the request finishes" hide in a callback? Work that takes time belongs to the implementation that owns it. The continuation is a phrase in the markup: requestable-after="#receipt.show()".
  • 5
    Why should every interaction be a bespoke listener you wire and clean up? Triggers bind their own listeners in connectedCallback and clean up on disconnect. An element carries on-*, implements, both, or neither.

What it is

A trigger grammar

One attribute per event; the value is a tiny phrase language — receivers, chains, keys, object literals and modifiers.

Customized built-ins

Every participating element is a host: is="interactable-<tag>". Forms, dialogs and details keep their native semantics.

No engine

A pure parser turns attribute strings into phrases; an executor runs them. Both are functions the host calls. No store, no signals.

State: three tiers

Authored, live and derived state, each in its place. The DOM is the store; ids are the addresses; whoever changes B fires A.

An asynchronous seam

Verbs are synchronous; chains never await. The network gap has a name and a place in the markup.

Signatures as strings

Every verb, config and state signature is a tsyntax string — the same string is the TypeScript type and the runtime check.

Shipped implementations

Fifteen capabilities register themselves on import. Each is one file, one defineImplementation call, tagged with the elements it may attach to.
